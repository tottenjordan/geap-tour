GEAP Workshop: a hands-on demo of the Gemini Enterprise Agent Platform — ADK agents with MCP tools, multi-model routing, evaluation, optimization, and governance on Google Cloud. The domain is corporate travel and expense management.

## Architecture

### Two agent topologies

1. **Coordinator agent** (`src/agents/coordinator_agent.py`) — a **direct-tools** agent: it holds all three MCP toolsets (search + booking + expense) itself and searches/books/checks/submits directly, plus `PreloadMemoryTool` (or `CachingPreloadMemoryTool`) for Memory Bank. It **delegates to nobody** — the two `AgentTool`s were removed 2026-08-20 after a trace census recorded 0 calls across 10 invocations, and a nested sub-agent MCP call doesn't stream through the managed runtime anyway. `travel_agent` (flights/hotels) and `expense_agent` (policy/submissions) remain as **independently deployed and evaluated** agents (`multi_agent_batch_eval --agents travel_agent`, `simulated_eval`, their own evalsets) — two deployables, not duplication. Its model is wrapped in `src/models/quota_retry.py:RetryingLlm` so a Vertex 429 becomes a slower answer, never an empty-at-200 stream (insurance: the coordinator took 0 of the 215 429s that hit the router). `RetryingLlm` also retries a **silent turn** — an inner generator that completes with no *visible* output (no text, no `function_call`, no `function_response`, no `error_code`) raises no exception, so it used to fall straight through to `return`: HTTP 200, zero characters, unretried, unlogged. A `function_call`-only hop is a normal tool hop and is deliberately **not** silence (retrying would re-run the tool); a turn that already emitted visible output is never retried. Exhausted retries yield a greppable `EMPTY_RESPONSE_PREFIX` reply with `error_code="EMPTY_RESPONSE"` so an eval sees a labelled infra failure, not a bad answer (opt out with `RetryingLlm(..., retry_empty=False)`). Both engines inherit it — the coordinator via `retrying_model()`, the router via `TierRoutingLlm._select`. **Those same wrappers hide `LiteLlm` from ADK's `isinstance(canonical_model, LiteLlm)` check** (`flows/llm_flows/contents.py`), so ADK strips the synthetic `adk-*` tool-call ids that Anthropic pairs tool results by, and a **multi-step Claude-tier turn** dies on `AnthropicError: 'tool_call_id'` → empty-at-200 (measured: lite/flash/pro 20/20 clean, the sonnet band 4/8 empty — router-specific, not a platform issue). ADK strips only the `adk-` prefix, so the precondition is a **mixed-tier session**: Claude's own `toolu_*` ids survive, and the stripped id must have been minted for an earlier *Gemini* hop (routine — the traffic generator reuses one session per user, and a 5-tier router sends consecutive turns to different tiers). Proved without a deploy by `uv run python -m src.eval.spike_tool_call_ids` (real Claude on Vertex, real `TierRoutingLlm`, pre-fix `RAISED 'tool_call_id'` → fixed `FULL`). `RetryingLlm` therefore calls `src/models/tool_call_ids.py:restore_tool_call_ids()` once per turn when `is_litellm_backed(inner)` — gated because Gemini *rejects* ids it never issued; pairs by name/order; fills only missing ids; replaces the nested `FunctionCall` rather than mutating it (parts are shallow copies shared with session events). Measure the rate with `uv run python -m src.eval.verify_router_health --agent-id <ROUTER_ENGINE_ID> [--repeat N --threshold 0.05 --json]` (7 tier-spanning probes, fresh session per turn, raw-SSE; silent empties counted apart from labelled ones and reported with a Wilson interval; exits non-zero above the threshold). See [docs/notes/router-empty-stream-retry.md](docs/notes/router-empty-stream-retry.md) and [docs/notes/coordinator-router-learnings.md](docs/notes/coordinator-router-learnings.md). **Four distinct causes have produced empty-at-200 here** (container recycle at `min_instances=1`, a 429 from an unbounded tool payload, an OOM SIGKILL at 4Gi on a LiteLlm tier, and this tool-call-id strip) — triage with [docs/notes/empty-at-200-field-guide.md](docs/notes/empty-at-200-field-guide.md) rather than assuming which one.

2. **Multi-model router** (`src/router/agents.py`) — 5-tier complexity router. A `before_agent_callback` calls the complexity classifier (`src/router/complexity.py`) which scores prompts 0–1, then routes to one of five sub-agents: lite (gemini-3.1-flash-lite) → flash (gemini-3.5-flash) → pro (gemini-3.1-pro-preview) → sonnet (claude-sonnet-4-6) → opus (claude-opus-4-6). The router itself runs on the lite model. Score boundaries (defaults, DOE-tuned for cost savings in screening doe-screening-20260812-073603): <0.44 lite, 0.44–0.60 flash, 0.60–0.80 sonnet, 0.80–0.95 pro, ≥0.95 opus. All four cut-points are env-overridable (`COMPLEXITY_LOW`/`MEDIUM_SPLIT`/`COMPLEXITY_HIGH`/`HIGH_SPLIT`).

### MCP server registration

Agents connect to MCP servers through two mechanisms in `src/registry.py`:
- **Agent Registry** (primary): `get_mcp_tools(server_name)` looks up the server by its registered resource name via `AgentRegistry.get_mcp_toolset()`.
- **Direct URL** (fallback): on any registry failure (`RuntimeError` control-plane error *or* `ValueError` missing endpoint URI) it falls back to the Cloud Run URLs in the `MCP_SERVER_URLS` mapping (`src/config.py`), logging the fallback at **WARNING** with the underlying error — a coordinator quietly running on the fallback path is exactly the silent degradation we want visible. Inside the managed Agent Engine runtime the engine runs under a per-engine `AGENT_IDENTITY`; registry resolution used to fall back on every request because that identity lacked `agentregistry.mcpServers.get` (a 403 wrong-principal IAM denial, **not** an unreachable API and **not** fixed by granting the RE service agent). **Remediated (2026-08-15):** grant `roles/agentregistry.viewer` to the engine's `principal://<effectiveIdentity>` (reproducible as "Step 0b" in `scripts/setup_governance_policies.sh`), then recycle cached toolsets with an in-place `deploy_agents … --update` (toolsets resolve once per container; a *recreate* mints a new identity and needs a fresh grant). The MCP servers also run **stateless HTTP** so Cloud Run scaling can't drop a session ("Session terminated" 404). See [docs/notes/agent-registry-mcp-resolution.md](docs/notes/agent-registry-mcp-resolution.md).

The three required env vars `SEARCH_MCP_SERVER`, `BOOKING_MCP_SERVER`, `EXPENSE_MCP_SERVER` hold Agent Registry resource names — these are NOT optional and will crash on import if missing. Verify all three toolsets actually resolve their real tools (turns a silent tool-less agent into a non-zero exit): `uv run python -m src.eval.verify_mcp_tools [--json]`.

### A2A (Agent-to-Agent) — preview-optional

`src/a2a/` makes the coordinator a discoverable A2A agent. `agent_card.py:build_agent_card()` builds an `a2a.types.AgentCard` (name `coordinator_agent`, five skills mirroring its real tools: flight/hotel search, booking, expense policy check, expense submission) whose endpoint derives from `config.coordinator_a2a_url()`; `agent_card_dict()` serializes it. `remote_agent.py:build_remote_coordinator()` returns an ADK `RemoteA2aAgent` (`google.adk.agents.remote_a2a_agent`) client, and `try_build_remote_coordinator()` returns `None` on any failure. `src/registry.py` adds `register_a2a_agent(card)` / `get_a2a_agents()` that reuse the same `AgentRegistry` client as the MCP flow. `src/deploy/register_a2a.py` is the CLI (register default, `--discover` to list).

This is **preview-optional**: the A2A/registry create+discovery surface may not be enabled in every project. Every path degrades gracefully — it logs `A2A preview not enabled — skipping` and returns `None`/`[]` (the CLI exits 0) rather than crashing a live run. `a2a-sdk` 1.x models are protobuf, so serialization uses `protobuf.json_format.MessageToDict` (with a pydantic `model_dump` fallback).

### Model resolution

`src/config.py:resolve_model()` resolves each model id by family: **Gemini 2.x** (and `models/` ids) pass as plain strings (regional endpoints); **Gemini 3.x** use the **native ADK `Gemini` class** on the global endpoint (`client_kwargs={"vertexai": True, "location": "global", "project": …}`) — LiteLlm mangles Gemini-3 thought signatures into bogus `function_calls`, so Gemini-3 must not go through it; **Claude** (and any other non-gemini id, incl. an explicit `vertex_ai/` prefix as an opt-in escape hatch) is wrapped in `LiteLlm(vertex_location="global")`. See [docs/notes/gemini3-native-model-resolution.md](docs/notes/gemini3-native-model-resolution.md).

**Every `GenerateContentConfig` this repo builds goes through `src/models/afc.py:with_afc_disabled`.** google-genai defaults *automatic function calling* **on** for any config that doesn't say otherwise, so every call took the AFC branch — logging an `AFC is enabled with max remote calls` INFO per request plus a once-per-worker-process WARNING (1000+ rows in 6h on the router). Two emitters had to be closed together: our own classifier call (`src/router/complexity.py`) and ADK's, which copies `agent.generate_content_config` verbatim onto the request — hence the kwarg on the coordinator (via `get_armored_generate_config`), `router_agent`, the five tier agents, and `travel`/`expense`. Behaviour-preserving: ADK runs its own function-calling loop and passes tool *declarations*, so the AFC function map is always empty. Invisible locally (the string only exists in google-genai ≥ 2.18.1; the dev venv is on 2.17.0), so tests assert config contents, never logs. See [docs/notes/genai-afc-warning.md](docs/notes/genai-afc-warning.md).

### Shared config

`src/config.py` is the single shared config for all agents (standalone, coordinator, router) and eval — `resolve_model()`, model defaults, engine IDs, and env-var names all live here. It's bundled into every Agent Runtime deployment via `extra_packages=["src"]` (`src/deploy/deploy_agents.py`), so the router imports it directly. (The router previously carried a self-contained `src/router/config.py` copy; that duplication was removed.)

### Memory Bank + Session wiring (deploy)

Cross-session recall only persists if the deployed engine is backed by managed services. `deploy_agents._build_app()` wraps **every** agent in `vertexai.agent_engines.AdkApp(agent=..., session_service_builder=_session_service_builder)` and passes that AdkApp to `agent_engines.create/update` — without a managed Session service scoped to the engine's own runtime id, the deployed engine fails every request with "Failed to create session". Memory-enabled agents (detected via `_wants_memory()` — any agent holding a `PreloadMemoryTool`) *additionally* get `memory_service_builder`. That set is wider than just the coordinator: the **router** reads and writes memory (it defines its own `save_memories_callback`), the **five tier agents** read only (preload tool, no save callback), and only **travel/expense** have neither — pinned by `tests/test_memory_wiring.py:TestRealAgentMemoryWiring`. Both builders return Vertex services scoped to `AGENT_ENGINE_ID` (`VertexAiMemoryBankService` / `VertexAiSessionService`). **Memory scope gotcha (see [docs/notes/memory-bank-app-name-scope.md](docs/notes/memory-bank-app-name-scope.md)):** Memory Bank keys memories by `{app_name, user_id}`, and on a *deployed* engine the runtime's `app_name` is the **reasoning-engine id**, NOT the agent's Python name — so `verify_memory` defaults the scope `app_name` to the bare engine id (an `_ENGINE_SCOPED` sentinel; explicit `--app-name` overrides, `app_name=None` scopes by user only). Reading under the old `"coordinator_agent"` name silently returned nothing even when facts existed. Two verifications, complementary: `uv run python -m src.eval.verify_memory --user-id <id> --engine-id <ENGINE_ID>` reads a user's persisted facts back from the *store* (`agent_engines.retrieve_memories`, engine-scoped), while `uv run python -m src.eval.verify_cross_session_recall --user-id alice --engine-id <ENGINE_ID>` proves genuine cross-session *recall* — it states a preference in session A, polls until facts appear, then opens a **brand-new session B** for the same user and checks the preference resurfaces via `PreloadMemoryTool` (not same-session context). Its probe is a pure-recall question ("remind me of my saved travel preferences") — a *booking* probe empties out on the probe engine — and it retries an empty probe stream (`--probe-attempts`, default 3). Prints `RECALL: PASS/FAIL`, exits non-zero on FAIL. **The verdict is a grounded judge, not a substring match** (`evaluate_recall`, judged against the facts the store actually holds via the shared deterministic `judge_client`): the old `any(signal in response)` check could not tell recall from its opposite — *"I don't have a saved **window** seat preference"* contains `window`, so it **passed** on the precise symptom of memory being broken, in a check marked critical in `demo_readiness --deep`. It fails closed on an empty stream, a judge error, or an unparseable verdict, and never falls back to substrings; `--signal` is now diagnostic (`signals_found`) only. To pre-populate the Memory Bank before a demo (rich console view, instant recall), `uv run python -m src.eval.seed_demo_memories --engine-id <ENGINE_ID>` writes curated persona facts (alice/dana/sam; alice's facts match the recall demo's window/Delta/Marriott signals) **directly** via `agent_engines.create_memory` — synchronous, engine-scoped, no async-distillation lag or cold-engine empty-stream to poll around — then reads them back to confirm and exits non-zero if any failed (idempotent: existing facts are skipped, so re-running enriches not duplicates; `--dry-run`/`--user`/`--app-name`/`--no-verify` supported). The organic path (drive a session → coordinator's `add_session_to_memory` → async distillation) is unreliable for a demo and persisted zero retrievable facts here (async lag + a `try/except: pass` callback + the app_name mismatch above), which is why seeding creates facts directly.

**Memory-preload latency knob (opt-in, `ENABLE_MEMORY_PRELOAD_CACHE`, default OFF).** ADK's `PreloadMemoryTool` runs a **blocking** `search_memory` before *every* internal LLM hop, and the query is the invocation's original message (constant across hops), so a multi-hop coordinator turn re-pays the same 3–5s Memory Bank retrieve each hop (see [docs/notes/coordinator-latency-attribution.md](docs/notes/coordinator-latency-attribution.md)). `src/agents/caching_preload_memory_tool.py:CachingPreloadMemoryTool` subclasses it and memoizes the retrieve per `(invocation_id, query)` — within one invocation the retrieve happens once; a *new* invocation always misses (fresh `invocation_id`) so there is **zero cross-invocation staleness** and cross-session recall is unaffected (validate with `verify_cross_session_recall` before baking in). `coordinator_agent._build_memory_tools` selects stock vs caching tool by the flag; the subclass keeps `_wants_memory()` (isinstance) true. Same opt-in pattern as `COORDINATOR_THINKING_BUDGET`: unset ⇒ byte-identical behavior. The caching tool also emits the **`coordinator.memory_preload`** span (`memory.cache_hit` / `memory.result_count` / `memory.invocation_id`, plus `memory.error` on a failed retrieve) — the 3–5s preload previously had zero trace presence, and `cache_hit` is the only way to see from a trace whether the per-hop collapse happened. Its companion **`coordinator.memory_save`** (in `save_memories_callback`, with `contextlib.suppress` deliberately the *outer* manager so `traced` records the exception before it's swallowed) makes a Memory Bank *write* failure visible instead of silent, and the same callback now publishes `model.id` / `memory.enabled` / `memory.cache_enabled` / `armor.server_side` alongside `session.id`/`user.id` on `invoke_agent` — `model.id` matters because the backbone moves with `COORDINATOR_MODEL` (bake-off, DOE, the 2.5 pin). Note the preload span only exists when `ENABLE_MEMORY_PRELOAD_CACHE=1`. **The subclass carries a verbatim copy of ADK's render** (ADK inlines it into `process_llm_request` with no hook to delegate to), so it rots silently on an ADK bump — 2.7.0 moved the memory block from `_append_dynamic_instructions` (system-instruction channel) to `_insert_transient_user_content` (a transient user turn) while leaving **both** methods on `LlmRequest`. `tests/test_caching_preload_memory_tool.py:test_render_matches_stock_adk` diffs a whole `LlmRequest` against the stock tool; keep it passing when bumping ADK. See [docs/notes/coordinator-router-learnings.md](docs/notes/coordinator-router-learnings.md) and [docs/notes/adk-2.7.1-dependency-refresh.md](docs/notes/adk-2.7.1-dependency-refresh.md).

### Evaluation

- **Batch eval** (`src/eval/multi_agent_batch_eval.py`): offline eval using `AgentInfo` descriptors (no live MCP connections). 6 metrics: response quality, hallucination, safety, tool use, instruction following, response match. **The engine is resolved per agent** — `router_agent` → `ROUTER_ENGINE_ID`, everything else → `AGENT_ENGINE_ID` — because the router is its own deployment; an explicit `--agent-id` still pins every agent (the bake-off relies on that). Before this, one engine served the whole run, so a bare invocation scored `ROUTER_EVAL_CASES` against a *coordinator* silently. **`tool_use_quality_v1` grades the `AgentData` events, not the response text**, so a run where no item calls a tool is unscorable — the run prints `Tool calls: N/M items invoked at least one tool` and names the reason when it skips, instead of quietly returning five metrics. Note `ROUTER_EVAL_CASES` is dual-purpose: it also feeds `complexity_metrics.run_complexity_accuracy_eval`, whose result publishes the alerting `agent_router/routing_accuracy_pct`, so editing those prompts moves a monitored series. See [docs/notes/router-tool-use-quality.md](docs/notes/router-tool-use-quality.md).
- **Simulated eval** (`src/eval/simulated_eval.py`): multi-turn eval against a deployed agent using Vertex AI's user simulator.
- **Eval configs** (`src/eval/agent_eval_configs.py`): test cases per agent plus `build_agent_info()` which constructs `AgentInfo` for offline eval.
- **`Client` and `types` come from `agentplatform`, never `vertexai`** — `vertexai.Client` is deprecated, and `agentplatform` ships in the same already-pinned `google-cloud-aiplatform` distribution (no dependency change). `agentplatform._genai` is a **separate copy**, not an alias (`agentplatform.types is vertexai.types` → False), so `src/eval/_sdk_patches.py` patches `agentplatform._genai._evals_common` to match: a client that moves without its patches silently reinstates the "Failed to parse agent run response" bug that collapses every rubric metric to ~0. `Client` + `types` + patches are one atomic unit, pinned by `tests/test_agentplatform_client.py`. `vertexai.init` (identical function object) and `vertexai.agent_engines` / `AdkApp` (cloudpickled into the served engine) are intentionally left alone, so `deploy_agents.py` and `seed_demo_memories.py` import from both packages on purpose. See [docs/notes/agentplatform-client-migration.md](docs/notes/agentplatform-client-migration.md).
- **Vertex eval pipeline** (`src/pipelines/`): the full eval DAG (deploy → traffic → batch ‖ simulated ‖ complexity → monitor → report) as a KFP v2 Managed Pipeline, submitted manually via `src.pipelines.submit` (workflow: `.github/workflows/eval_vertex.yaml`). Replaced the old GitHub-Actions eval job graph. See [docs/notes/vertex-eval-pipeline.md](docs/notes/vertex-eval-pipeline.md).
- **Traffic generator** (`src/traffic/generate_traffic.py`): reuses one session per user by default (a thread-safe `SessionPool`) so `create_session` is called once per user, not once per query — the shared session-creation rate (not per-replica compute) is the throughput ceiling, so raising `min_instances` does not help. `--no-reuse-sessions` restores legacy per-query behavior; a stale reused session is invalidated and retried once. See [docs/notes/traffic-session-reuse.md](docs/notes/traffic-session-reuse.md).
- **Periodic-snapshot quality eval (two honest surfaces)** — the canonical source is the **offline-eval bridge**. The native Vertex Online Evaluators return `INSUFFICIENT_DATA` under a default deploy, but this is **NOT** a hard content strip (root cause corrected 2026-08-15): the managed `AdkApp` runtime's `set_up()` forces the ADK span-content gate closed unless deployed with `AdkApp(enable_tracing=True)`. That lever is wired behind the opt-in `ENABLE_SPAN_CONTENT_CAPTURE` flag (default OFF, since it writes prompt/response into Cloud Trace) and was **validated live** (46/46 `call_llm` spans carry real content). The offline bridge remains the canonical shipped surface **by choice** — model-neutral, no privacy-off capture on the served engine; the native online path is unblockable on demand. See `docs/notes/online-eval-content-capture.md`, `docs/notes/offline-eval-monitoring-bridge.md`, and memory `online-eval-content-capture-blocked`. The coordinator (a task executor) and the 5-tier router (an economic optimizer) get **separate series** so they are never scored on the same axis:
  - **Coordinator quality → `custom.googleapis.com/agent_eval/*`** (1-5 rubric, alert `< 3.0`). `src/eval/publish_offline_eval.py:publish_offline_scores()` extracts the three monitored quality metrics (`helpfulness`, `tool_use_accuracy`, `policy_compliance`) from the batch eval — which legitimately scores the *deployed* engine via the Vertex Gen AI Evaluation Service — scales them 0-1 → 1-5, tags them `eval_mode=offline`, and delegates to `src/eval/publish_eval_metrics.py:publish_eval_metrics()` (names strictly from `quality_alerts.ALL_MONITORED_METRICS` — no drift). Two of the three (`policy_compliance` and `tool_use_accuracy`) are custom pointwise `LLMMetric`s that the `client.evals` SDK can't score (`400 Error parsing JSON`), so `_apply_standalone_judges()` overwrites them in the batch via standalone judges before publish — `policy_judge.py` and the delegation-aware `tool_use_judge.py` (`geap_tool_use`, which — unlike the delegation-blind SDK `TOOL_USE_QUALITY` — does not penalize the coordinator's `transfer_to_agent` routing; see [docs/notes/coordinator-tool-use-quality.md](docs/notes/coordinator-tool-use-quality.md)). Both publish paths (`publish_offline_eval --run` and `run_all_evals`) run them. For higher-trust scoring, `src/eval/judge_panel.py` runs a **diverse cross-generation Gemini judge panel** (`gemini-2.5-flash` + `gemini-3.5-flash`, all `temperature=0` via `judge_client`) aggregated by **median** with **Krippendorff-alpha inter-rater reliability**, so no single autorater's bias decides a verdict — opt-in via `policy_judge.run_policy_compliance_eval(panel=True)`; the generic `score_pairs_with_panel` is reusable by the other pointwise judges (roadmap P1.4). The panel is **Gemini-only**: the genai `generateContent` path `judge_client` uses only reaches Google-published models (a Claude/partner judge 404s under `publishers/google`, verified live 2026-08-18), so `judge_client.resolve_judge_location` mirrors `resolve_model`'s family split (Gemini-3 judged on the *global* endpoint, Gemini-2 regional) and panel diversity spans Gemini *generations*, not vendors.
  - **Tool-call faithfulness → `custom.googleapis.com/agent_eval/tool_faithfulness`** (1-5, alert `< 3.0`; also on `agent_online_eval/*`). Audits whether the coordinator's response is **truthful about the actions it performed** — a **hallucinated action** is a reply claiming a completed action ("I booked FL001", "I submitted your expense") with no matching executed tool. This is the gap `tool_use_judge` explicitly does **not** cover: it scores only `(prompt, final-response-text)` via `client.evals.run_inference`, which yields text but **no trajectory**. `src/eval/tool_faithfulness.py` therefore captures both the visible response *and* the real executed trajectory in one **`stream_query`** pass (`trajectory_eval.capture_trajectory`, not `run_inference`), then a **grounded LLM judge** compares completion claims against the ground-truth tool list and names fabrications (`Hallucinated: … / Score: 1-5`). Published offline via `publish_offline_eval._inject_tool_faithfulness` (in `_apply_standalone_judges`, guarded) and online via `online_monitor.run_online_faithfulness` (`--faithfulness`, requires `--agent-id`). Primary score counts only *hallucinated* (claimed-not-executed) actions; executed-but-unreported is out of scope. **Load-bearing assumption — RESOLVED LIVE (Branch A, 2026-08-18):** coordinator-level accuracy assumes the client stream surfaces nested sub-agent MCP calls (Branch A) vs only `transfer_to_agent` (Branch B); `src.eval.spike_trajectory_visibility` ran against the probe engine and confirmed **Branch A** — the coordinator surfaces the real nested domain calls (`booking_mcp_book_flight`, `search_mcp_search_hotels`) with matching responses, so faithfulness is **action-level** as designed. Validated end-to-end live 2026-08-18: clean cases score 5.0, synthetic fabrications are flagged (`book_flight`/`submit_expense`/`book_hotel`), and the `--threshold` gate exits 1 below / 0 above. `include_transfers`/injectable `engine`/`cases` keep the sub-agent-engine fallback a config change if a future backbone stops surfacing nested calls (re-run the spike then). See [docs/notes/tool-call-faithfulness.md](docs/notes/tool-call-faithfulness.md).
  - **Router efficiency → `custom.googleapis.com/agent_router/*`** (native units). `src/eval/publish_router_efficiency.py:publish_router_efficiency()` publishes `routing_accuracy_pct` (%, alert `< 80`), `cost_savings_pct` (% vs all-Opus baseline, alert `< 50`), and `classifier_latency_ms` (ms, alert `> 8000`) **verbatim, no scaling**, from the complexity accuracy + cost-efficiency evals. Cost savings was previously computed and discarded; it is now a first-class monitored series. Alert directions/families are parametrized in `quality_alerts.ROUTER_MONITORED_METRICS`.
  - `run_all_evals` publishes both surfaces as its Phase 6 step; each CLI (`publish_offline_eval`, `publish_router_efficiency`) can publish standalone (`--from-json`/`--latest`/`--run`/`--dry-run`). `src/eval/verify_monitors.py` reads both series as two blocks (`coordinator_quality` + `router_efficiency`, canonical source; optional guarded BigQuery export via `--source bigquery`). The dead native `onlineEvaluator` setup and its deprecation shim were removed.
  - **Managed engine-health alerts (the platform's own metrics)** — all the alerts above fire on our self-reported `custom.googleapis.com/*` gauges (`resource.type="global"`, only present while our traffic generator / eval publishers run). `quality_alerts.create_engine_health_alerts()` adds **two** policies on the **authoritative server-side** metrics the Agent Runtime emits automatically on `resource.type="aiplatform.googleapis.com/ReasoningEngine"` — `_build_engine_latency_policy` (p99 `reasoning_engine/request_latencies` > `ENGINE_LATENCY_P99_MS`=5000ms, ALIGN_PERCENTILE_99) and `_build_engine_error_rate_policy` (a numerator/denominator ratio: 5xx `request_count` rate over total rate > `ENGINE_ERROR_RATE`=5%, ALIGN_RATE). Both group by `reasoning_engine_id` so each deployed engine (probe/pinned/bake-off) is evaluated on its own series, and both page on genuine engine degradation with **no client-side instrumentation running** (mirrors the [runtime monitoring doc](https://docs.cloud.google.com/gemini-enterprise-agent-platform/scale/runtime/monitoring)'s p99-latency>5s alerting example). Wired into `setup_all_alerts` (the `quality_alerts all` subcommand). The managed engine metrics + auto "Agent Runtime Overview" dashboard are zero-setup (no descriptor seeding); viewing them needs `roles/monitoring.viewer`, granted alongside `roles/logging.viewer` by `scripts/setup_logging_sink.sh`.
- **CI/CD eval gate (advisory, opt-in)** — a demo PR quality gate that doesn't slow dev, in two tiers (see `docs/notes/ci-eval-gate.md`). **Tier 1** (`tests/test_eval_gate_safety.py`) is a deterministic, no-cloud corpus check (adversarial prompts must be refused by `input_guardrail_callback`, benign ones must pass) that runs inside the already-required `tests.yaml`. **Tier 2** (`.github/workflows/eval_gate.yaml`) reuses `multi_agent_batch_eval` (via the new `--limit`/`_select_cases`) to score the coordinator on rubrics; it is label-gated (`run-eval`) / `workflow_dispatch`, WIF-skip-guarded, writes a PASS/FAIL table to `$GITHUB_STEP_SUMMARY`, and is intentionally **not** a required check (advisory). Requires repo vars `WIF_PROVIDER`/`WIF_SERVICE_ACCOUNT`/`AGENT_ENGINE_ID` and a `run-eval` label. **The repo var `AGENT_ENGINE_ID` is a second, independent copy of the engine id and it drifts** — on 2026-08-21 it still held `4709…`, a 9-day-stale `router_agent` labelled `demo: macys-agent-designer` (not our solution) sitting on the 4Gi default with 2 critical config failures, so every CI run scored the wrong engine and called it coordinator quality. Re-point it whenever `.env`'s `AGENT_ENGINE_ID` changes: `gh api -X PATCH repos/<owner>/<repo>/actions/variables/AGENT_ENGINE_ID -f name=AGENT_ENGINE_ID -f value=<id>`; confirm with `verify_engine_config --engine-id "$(gh variable list --json name,value ...)"`. Honest limit: rubric scoring needs a *deployed* engine (no local-inference path), so the gate scores the shared `AGENT_ENGINE_ID` engine, **not the PR diff** — a regression alarm + capability demo, not a per-diff gate.

### DOE experiments & the coordinator model bake-off

`src/doe/` turns the single-config eval pipeline into an experiment engine: a declarative `Factor` registry (`factors.py`) → fractional-factorial `build_design()` → **one Vertex `PipelineJob` per design point** (`launch.py`, subprocess-per-point so each point's env bakes at import time) → `harvest.py` (one row per point) → `analyze.py` (main effects + cost-quality frontier → `report.md`). `run_doe.py` is the CLI (dry-run default; `--execute` opt-in because `engine_env` factors deploy a fresh engine per point). See [docs/notes/doe-framework.md](docs/notes/doe-framework.md).

The **coordinator model bake-off** compares two coordinator deployments that differ only by backbone — `gemini-3.6-flash` (baseline, coded `-1`) vs `claude-sonnet-5` (candidate, `+1`). It borrows the `model_backend` factor (`factors.py`, coordinator-only: moves just `COORDINATOR_MODEL`, sub-agents fixed) to define the two backbones in one place, but `run_bakeoff` **owns the deploy/teardown lifecycle directly** rather than running the DOE PipelineJob fan-out (whose ephemeral per-point engines get deleted in the pipeline's exit handler before pairwise/traffic can reach them, and whose manifest never records an `engine_id`). It deploys **two persistent engines**, one subprocess each via `src/doe/deploy_coordinator.py` (so `COORDINATOR_MODEL` bakes at import time; the child prints its resource on a `BAKEOFF_ENGINE:` marker line), records both `engine_id`s in the run **manifest** (not `.env`, which holds only one coordinator id), and **tears both down in a guaranteed `finally`** (`--keep-engines` opts out). Three evidence streams fuse into one verdict:
- **Offline rubrics per engine** — `run_bakeoff` scores each *deployed* engine with `multi_agent_batch_eval` (mapping versioned metric keys → base names via `harvest._metric_base`/`BATCH_METRICS`); cost is **measured**, not assumed — `collect_token_usage` reads real `usage_metadata` off `stream_query` (isolated in the bake-off, not shared `_sdk_patches.py`) and `src/eval/cost_model.py` prices it fairly (Gemini per-token, Claude GSU→USD — constants are directional, verify before quoting); no usage → honest `n/a`, not a fake `$0`.
- **Pairwise SxS** (`src/eval/pairwise_eval.py`) — `PairwiseMetric` autorater (`flip_enabled`, `sampling_count=4`) → win-rate, with a standalone `google.genai` `Choice: A|B|TIE` fallback if the managed template 400s. `--from-manifest` picks gemini=baseline, claude=candidate.
- **Per-model-labeled traffic** — `generate_traffic --label model=<id>` keeps the two deployments as separate Cloud Monitoring series; `verify_monitors --group-by model` and the dashboard's per-model breakdown tiles read them back split (default ungrouped behavior unchanged).

`src/doe/bakeoff_report.py` (pure assembly) renders offline means + delta, pairwise win-rate, online p50/p95/error, and per-request $ with a one-line verdict → `bakeoff_report.md`. `run_bakeoff` also records **one Vertex AI Experiments run per backbone** (`src/observability/experiments.py:log_run`, best-effort; params `backbone`/`role` + scalar metrics) into the `coordinator-bakeoff` experiment — kept strictly separate from the router's `router-efficiency` experiment. Dormant by default (`--experiment-name`, default `coordinator-bakeoff`; `''` disables). `src/doe/run_bakeoff.py` chains all phases (preflight → deploy 2 → offline+cost → pairwise → traffic → verify+report → teardown), **dry-run by default** (mirrors `run_doe`); every phase entrypoint is injectable for offline wiring tests. Caveats: dataset ~50 curated cases (incl. multi-step + adversarial) not ≥1000; Gemini-only judge; self-driven traffic split (no native endpoint A/B). See [docs/notes/coordinator-model-bakeoff.md](docs/notes/coordinator-model-bakeoff.md).

### Security layers

- **Model Armor** (`src/armor/config.py`): server-side screening via Model Armor templates + client-side guardrail (blocklist patterns, length limits). This is the single shared module — both the coordinator and the router import it (the router previously had a duplicate `src/router/armor.py`, now removed). The pure validator `input_guardrail_callback` (Content|None) stays side-effect-free for testability; `guardrail_with_telemetry` wraps it to emit a `guardrail.blocked` OTel span event + a `custom.googleapis.com/agent_armor/blocked` metric on each block (telemetry is fully guarded and never changes the guard's decision). The coordinator wires `guardrail_with_telemetry` as its `before_agent_callback` and passes `generate_content_config=get_armored_generate_config(COORDINATOR_MODEL)` for server-side armor; the router runs `input_guardrail_callback` inside its `complexity_router_callback`. Server-side Model Armor is **model-family-aware**: `get_armored_generate_config(model)` attaches the region-scoped templates only for a Gemini-2.x backbone (where they're honored natively); Gemini-3 runs on the global endpoint (templates `400 TEMPLATE_NOT_FOUND`) and Claude runs via LiteLlm, so armor is omitted for both and the client-side guardrail is the guaranteed layer (see [docs/notes/gemini3-native-model-resolution.md](docs/notes/gemini3-native-model-resolution.md)). A project-level Model Armor **floor setting** (inspect-only) with **Cloud Logging** on (`scripts/setup_model_armor_floor_settings.sh`), plus template `logSanitizeOperations` (`scripts/setup_model_armor.sh`), feed the console Security-tab Model Armor dashboard; two caveats — our custom Cloud Run MCP servers aren't "Google Cloud MCP Servers" (that floor setting is a no-op for them), and floor-setting/template screening covers the Gemini `generateContent` path so the dashboard is richest with a native Gemini backbone. See [docs/notes/model-armor-security-dashboard.md](docs/notes/model-armor-security-dashboard.md). On the **same regional-Gemini gate**, `get_armored_generate_config` also attaches the opt-in coordinator **latency knobs** `COORDINATOR_THINKING_BUDGET` (0=off / -1=dynamic / N=cap) and `COORDINATOR_MAX_OUTPUT_TOKENS` — both default unset (byte-identical config to before) because uncapped default "thinking" dominates the coordinator's time-to-first-token. `src/eval/latency_probe.py --agent-id <ENGINE_ID>` buckets the managed `request_latencies` by phase (startup/mcp_tool/llm) to prove where the ~17s p50 goes (MCP cheap; startup + Memory Bank preload dominate). See [docs/notes/coordinator-latency-attribution.md](docs/notes/coordinator-latency-attribution.md).

## Key Conventions

- All agents export `root_agent` at module level plus `agent = SimpleNamespace(root_agent=...)` for ADK CLI compatibility.
- Agent instructions that say "GEPA-optimized" were produced by the optimizer — edit these only through re-optimization, not manually.
- MCP servers use FastMCP with `streamable-http` transport.
- **Bound every list-returning MCP tool.** The mock DBs are unbounded module-level accumulators on long-lived Cloud Run instances; an uncapped payload is what tripped the Vertex `GenerateContent` quota and turned the router's answers into empty-at-200 streams. `get_user_expenses` (`MAX_EXPENSES_RETURNED`) and `list_all_bookings` (`MAX_BOOKINGS_RETURNED`, capped 2026-08-20) both return `{total_count, returned_count, truncated, <records>}` newest-first, and their docstrings tell the model to report truncation honestly. See [docs/notes/router-empty-responses-quota.md](docs/notes/router-empty-responses-quota.md).
- **EVERY engine needs more than the default 4Gi — not just LiteLlm ones.** Agent Runtime defaults to `cpu 4 / memory 4Gi`, which OOM-kills a worker mid-call: the client gets HTTP 200 with **zero characters**, there is no traceback, no shutdown log (a SIGKILL emits none), and the Cloud Trace loses its enclosing `invoke_agent` span. Measured twice, on backbones we assumed were different causes: router `6134…` 8/8 empty on Claude-tier probes → **0/8** at 16Gi, and a **Gemini-only** coordinator `4380…` 22/147 empty (180 empty *attempts*) → **0/147, 0 attempts**. The Gemini case is why `deploy_agents._auto_memory()` no longer conditions on `needs_litellm()` — it returns `{"cpu": "4", "memory": "16Gi"}` for **every** agent. `--memory 32Gi` overrides. Unconditional, not a flag to remember — the router already has one mandatory-flag trap (the tier env overrides). 16Gi is the *measured* value; 8Gi was never tested. `TierRoutingLlm.generate_content_async` also logs every dispatch (`Tier dispatch -> <model> (litellm_loaded=…)`), any exception, and a zero-response turn; without it a Claude failure produced no log line at all. See [docs/notes/empty-at-200-field-guide.md](docs/notes/empty-at-200-field-guide.md) and [docs/notes/router-claude-tier-oom.md](docs/notes/router-claude-tier-oom.md).
- **A merged fix is not a deployed fix.** Serving config drifts silently: the engine keeps returning 200, health checks pass, and nothing logs. `src/deploy/engine_baseline.py` is the **executable** baseline (rules as data, each with a `why`, importing `LITELLM_MEMORY`/`LITELLM_CPU` from `deploy_agents` so verifier and deployer cannot diverge) and `src/deploy/verify_engine_config.py` diffs a live spec against it, exiting non-zero on **critical** drift only (advisories never fail CI, or the suite gets suppressed). It catches the silent class: a 4Gi container, router tiers regressed to Gemini-3 by a plain `--update`, a thinking `CLASSIFIER_MODEL` collapsing all traffic onto the lite tier, `ENABLE_MEMORY_BANK=0`, a non-`AGENT_IDENTITY` engine. Its first run found the `.env` coordinator `3639…` still on 4Gi three days after the fix merged (remediated in place via `updateMask=spec.deploymentSpec.resourceLimits` — ~4 min, no repackage, no recreate). Creates now also get `DEFAULT_MIN_INSTANCES=1`; **updates deliberately pass `None`** so a routine `--update` never downgrades an engine already running 4. See [docs/notes/deployed-engine-baseline.md](docs/notes/deployed-engine-baseline.md).
- Tests validate agent configuration (tool count, sub-agent names, callback presence) without requiring live GCP or MCP connections.
- `.env` is the source of truth for deployed engine IDs — `deploy_agents.py` auto-updates it after each deploy.
- SDK-first demo notebooks live in [`notebooks/demo/`](notebooks/demo/) (platform + evaluation tours on this repo's modules); every live/billable cell is opt-in behind a `GEAP_RUN_*` flag, and the eval notebook uses the offline bridge (native Online Evaluators are off by default — unblockable via `ENABLE_SPAN_CONTENT_CAPTURE`, see `docs/notes/online-eval-content-capture.md`). See [notebooks/demo/README.md](notebooks/demo/README.md).
